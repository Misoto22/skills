`sync` 把本地仓库和远端对齐，然后明确说出哪些地方没对上。它 fetch、清掉上游已消失的跟踪引用、把基线分支快进，并报告每一个需要你做决定的分支——但不替你做其中任何一个决定。

## 它只做快进

分支一旦分叉，在 rebase、merge 和 reset 之间选哪个是你的判断，猜错就会毁掉工作。所以它只快进能快进的，其余的如实报告。

一次没被要求就执行的 rebase，和丢失工作是无法区分的——这就是为什么这里没有一个开关能打开它。

同一条规则还带来两个更小的拒绝。标签只 fetch，从不 prune：`--prune-tags` 会删掉所有远端没有的本地标签，包括你五分钟前手工打的那个，而一个标签有时是某个提交唯一的可达路径。以及，工作树脏导致快进被拒时，它会报告是哪些文件挡住的——替你 stash 正是未提交的工作消失的方式。

## 它先报告，再写入

开头那份报告的每一行，都来自一条不写任何东西的命令：工作树状态、当前分支相对上游的位置、基线落后多少、prune 之后哪些分支失去了上游、有哪些 worktree。

```
Sync <repo> → <base>
  working tree   clean
  current branch feat/x  ahead 2, behind 0
  base main      behind 7
  gone upstream  none
  worktrees      3
```

没有任何命令能填的字段会报为 unknown——不估算，也不悄悄省略。

## 然后它告诉你，你的分支处在什么状态

基线分支会被快进。你的功能分支拿到的是一句话：

| 状态 | 它会告诉你 |
|---|---|
| 没有上游 | 用 `-u` 推一次来建立上游 |
| 只领先 | 有未推送的工作 |
| 只落后 | 准备好了就 rebase 到基线上 |
| 已分叉 | 领先 N、落后 M——rebase 还是 merge，你决定 |
| 上游消失 | PR 多半已经合并、分支被删了；`/dev:cleanup` 负责清掉它 |

加上 `--all` 时，每个本地分支都按同样的方式分类，严格落后的那些会在不 checkout 的情况下被快进。被别的 worktree 占用的分支会跳过并说明原因——那是一个事实，不是错误。

## 它不做什么

它不负责发布改动、不删分支、不解决合并冲突。它从不 rebase、从不 reset、从不丢弃任何一个本地提交。所有它拒绝替你决定的事，都会收在最终报告的 `attention` 里，把选项列出来，一个都不替你选。
