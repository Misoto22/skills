一次改动发布之后，残留会留下来：本地分支、它在远端的副本、当时用的 worktree，有时还有一个 `git mv` 看不见的、只装着被忽略文件的目录。`cleanup` 只删这些，凡是它说不清来历的一律不动。

## 「合并了没有」这个问题要问 forge，不能问 git

rebase 或 squash 合并会重写提交，所以 `git branch --merged` 根本列不出一个真的已经合并的分支。照 git 的答案删，删掉的是不该删的；照它保留，则每一个 squash 合并过的分支都会永远留着。

所以这里每一次删除都要拿 forge 验证——分支对应的 PR 必须报告 `MERGED`。没有 PR 的分支也不会被默认当作废弃：只有 `git merge-base --is-ancestor` 证明它的每一个提交都已经在基线上，才可以删；并且报告里会写明是哪一项检查放行的，否则「没有 PR」和「已删除」摆在一起看着很吓人。

远端会被问两次，一次问已合并、一次问开着的，因为这两者不是对立面。一个分支可以既有一个已合并的 PR，又有一个更新的、开着的 PR——而 GitHub 会关闭任何以被删分支为头的 PR。

## 动手之前，先把一切列出来

第一遍什么都不写。它打印一张表：找到的每一个分支、远端分支、worktree 和残留目录，对每一个查到了什么，以及打算怎么处理。`--dry-run` 到此为止。

默认跑四遍；`--branches`、`--remote`、`--worktrees`、`--residue` 可以只跑其中一项，而 `--no-remote` 保留其余三项去掉远端那一项——适用于你没有推送权限的 fork。

残留这一项值得解释一下。它删的是只装着被忽略文件的目录，这些目录之所以被留下，是因为 `git mv` 只搬 git 跟踪的东西——比如几个月前 `.py` 文件搬走后剩下的 `__pycache__`。而一个**紧挨着**被跟踪文件的忽略目录是工作状态，不是残留，会保留：删掉一个构建缓存的代价是重新构建一次，删掉一个 `.venv` 的代价是一个下午。

## 「保留」那张表才是重点

最终报告有两张表：删了什么，和留下了什么。要读的是第二张。里面的每一行都是看起来该删、但实际不该删的东西，并且都写明了原因——未合并的分支、还有开着 PR 的远端分支、脏的 worktree、旁边还有被跟踪文件的忽略目录。

凡是仅仅因为「需要人来决定」而没动的，会作为一个问题问出来，而不是塞进「保留」里被忘掉。最常见的一种是：一个已合并的分支正在你的主仓库里被 checkout 着——这时候那个 checkout 本身才是残留，但分支名往往是你当时做到哪儿的唯一记录，所以它只是提议，不会直接给你切走。

## 它不做什么

它不丢弃未提交的工作、不 reset 分支、不删除没给你看过的未跟踪文件。任何有内容的 worktree——包括只有未跟踪文件——都会保留。本次运行所在的 worktree 无论什么状态都不会被删：在里面是撤销不了这个删除的。以及，一个远端被删但并没有合并的分支会被保留并标记出来，因为那要么是废弃的工作、要么是别人的失误，而本地副本一旦没了就找不回来了。
