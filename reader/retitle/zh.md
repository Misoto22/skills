每个 agent 客户端都拿你随口说的第一句话给对话命名。一周之后，侧边栏就是一列句子——没有日期，没有结构，扫不动。`retitle` 用一种结构取代它，并且两头都管：hook 在新会话开始时命名，批量整理负责已经堆在那里的旧会话。

## 命名规范

```
MMDD｜类型｜主题
```

三个字段，顺序就是让侧边栏可用的顺序。`MMDD` 取对话**创建**那天的月日，列表因此保持按时间排列——三周后重开的会话不会跳到最前面。`类型` 是九种工作方式之一。`主题` 是这次对话真正在讲什么，四到十二字，写对象而不是写活动。

分隔符是全角竖线 `｜`（U+FF5C），不是 ASCII 竖线。这不是为了好看：ASCII 竖线会把这个 skill 用来预览改名的那张 Markdown 表格拆散。

| 类型 | 什么时候用 |
|---|---|
| 功能 | 新能力、新接口、新页面 |
| 设计 | 写代码之前定下的形状——架构、接口、布局 |
| 修复 | 某处行为错了，已改正 |
| 优化 | 行为本来就对，改的是速度、成本或清晰度 |
| 发布 | commit、PR、合并、打 tag、部署 |
| 探索 | 试了一下看会怎样，没有确定的产出 |
| 文档 | README、注释、指南、changelog |
| 审计 | 拿你已经拥有的东西对标准检查 |
| 研究 | 读外部世界来回答一个问题 |

最后两个值得多看一眼。两者都以一份报告收尾、都不产出东西，所以界线画在**对象**上：审计检查的是你自己拥有的东西，研究读的是外部世界。「审查一下网站 SEO」是审计；「哪些 SEO 工具值得用」是研究。

## 实时的那一半

手动改名是打不赢的。客户端开新会话的速度比谁改名都快，所以规范必须落在会话诞生的地方——一个 `UserPromptSubmit` hook，在应用这个 skill 时装进 `~/.claude/scripts/`。

它在会话的第一个 prompt 触发完整规则，之后每五个 prompt 触发一次短复查：会话的方向会漂移，但完整规则太长，每轮都注入不划算。复查只在主题真的变了时才改名——一个每几条消息就变的标题，比一个略微过时的更糟。

其中两个决定值得知道。日期由 hook 自己解析，取自 transcript 的第一个时间戳而不是当前时钟，所以跨午夜的会话保持开始那天的日期。以及所有失败路径都静默 exit 0——一个会抛异常的 hook 会拦住你的 prompt，没有任何命名方案值这个代价。

## 批量的那一半

```
/dev:retitle
```

它读取每个客户端已有的会话，把每一条改名提案列成一张两列表格，然后停下。写入之前一定先确认，无论带了什么参数：几百个标题被改写在一个你没法轻易 diff 的存储里，不是「预览可以跳过」的那类操作。

主题推不出来的对话原样保留，并计入「跳过」。一个自信地写错的标题比一个乱但诚实的更糟，因为那是你会信的那个版本。

Codex 那边的写入走 app server 的 `thread/name/set`，不是 SQLite 目录表——那张表是派生的读模型，直接写进去，扫描器下次对账就会还原。权威存储在写入前会先备份。

## 它不做什么

它只改名字。不碰对话内容、不碰所属项目、不碰置顶、归档或排序。它不重命名项目、文件夹、分支、worktree 或文件。而对于一个它没有被验证过能理解的客户端，那张提案表格就是全部交付物——它不会靠猜 schema 去动一个存储。
